= Delivery lifecycle
:description: Explain accepted, queued, delivered, and failed stages for Notification Hub send records.

When Notification Hub accepts a send, it stores a delivery {gt-record} and (in this demo) moves that record quickly to a terminal {gt-delivery-status}.
You can talk about `accepted` vs `delivered` without reading provider logs.

== Status path after a send

After a send is accepted, Notification Hub stores a delivery record and moves it through demo statuses.

[mermaid]
....
flowchart TD
  Send["📱 &lt;b&gt;Sender&lt;/b&gt;&lt;br/&gt;sends a notification"] --> Accepted["🔔 &lt;b&gt;Notification Hub&lt;/b&gt;&lt;br/&gt;sets status to `accepted`"]
  Accepted --> Queued["🔔 &lt;b&gt;Notification Hub&lt;/b&gt;&lt;br/&gt;sets status to `queued`"]
  Queued --> Delivered["🔔 &lt;b&gt;Notification Hub&lt;/b&gt;&lt;br/&gt;sets status to `delivered`"]
  Queued --> Failed["🔔 &lt;b&gt;Notification Hub&lt;/b&gt;&lt;br/&gt;sets status to `failed`"]
....

== Delivery stages

`accepted`::
`POST /api/v1/send` succeeds when the request is valid, the {gt-template} exists, and {gt-preferences} allow the {gt-channel}.
The response includes a `recordId`.

`queued`::
The record exists and is waiting for simulated delivery.

`delivered` or `failed`::
The demo updates status; successful demos usually show `delivered`.
